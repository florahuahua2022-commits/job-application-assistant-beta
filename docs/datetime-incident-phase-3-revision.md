# 阶段三审阅修订

基线 `ae4c60b`，仍在 `codex/production-datetime-incident`。本说明修订原阶段三说明中的成功更新和待确认出口行为；不推进阶段四。

## 已确认成功：全局数据与当前视图分离

- `finishSave` 保留当前账号及请求序号校验，取消以视图上下文否决已确认成功的判断。
- `saveProfile`、`saveApplicationProfileDetails`、`saveDetectedContact` 的有效成功响应总是调用 `setProfile`，即使用户已经切换申请。
- `updateSavedJob`、`saveApplicationJobIdentity` 以及原职位表单的PATCH成功响应，总是更新列表中对应申请；不会因切换视图而丢失已保存数据。
- POST成功即使已切换视图，也调用原有 `refresh()` 并提示职位已保存；不打开新创建的申请，不清空当前表单。若刷新失败，仍明确保存已确认、列表可另行刷新。
- 表单重置、`openApplication`、确认/质量检查状态清除、普通通知仍受上下文约束；POST已保存通知按要求是例外。账号及请求序号隔离没有放宽。
- 资料主表单不再直接用全局 `profile.updated_at` 作重挂载key；仅当前上下文的成功保存更新一个key引用，避免迟到 `setProfile` 导致当前输入被重置。该引用只保存序号，不保存任何输入或草稿。识别结果变化引起的既有表单行为保留。
- 当前账号首次成功读取资料仍进行一次表单初始化，确保非受控下拉选项采用已保存值；之后的后台更新不重复初始化。初始化标识只保存账号，不保存资料或草稿，退出时清除。测试已先证明无初始化时title错误显示为空，再验证Dr、permanent_resident、one_month、concise_direct四个非默认值及保存后资料不被默认值覆盖。
- 原“迟到重载不覆盖当前申请文档”及A→B→A期间旧成功回调不重开申请、不覆盖新输入的场景保留。全局记录数据可以更新，当前选中申请不被切换。

## 由用户主动退出待确认

待确认文案现在说明完整下一步：先检查已保存职位，确认没有保存后点击「确认没有保存，重新保存」，再点击 Save Job。

新出口仅在用户点击时清除对应入口的待确认错误并更新请求序号，使Save Job恢复可用；不清空输入，不发POST，不自动重试，不自动判定未保存。再次点击Save Job才发送下一次请求。该操作代表用户主动判断，仍不承诺服务端幂等。

## 联系信息重试的实际验证方式

继续只有资料保存、职位保存两个独立浏览器测试入口，没有新增第三个测试入口。

资料保存场景已实际覆盖：合成简历上传响应提供可识别姓名、电话、邮箱 → 自动联系信息保存返回500 → 显示「重试保存联系信息」 → 点击后挂起PUT `/profile` → 切换申请并编辑当前输入 → 释放成功响应 → 全局联系信息更新、错误清除、当前输入保持。上传响应完全由离线夹具提供，不验证文件解析，也不调用后端。

资料主表单及申请内资料编辑也分别覆盖切换视图后的全局更新。职位场景覆盖两个编辑入口的全局列表更新、后台POST成功后的列表刷新/通知且不打开申请，以及用户主动解除待确认后“先恢复按钮、无POST；再点击保存、才发POST”。

## 「检查已保存职位」复用refresh的完整范围

仍仅调用原有 `refresh()`，没有新的读取接口或轮询。该函数原本会：

1. 在主页（非applicationsPage）执行 POST `/resumes/risk-scan`，取得简历风险扫描结果。
2. GET `/profile`：刷新全局资料。
3. GET `/resumes`：刷新简历及其风险提示；沿用原有简历状态联动行为。
4. GET `/applications`：刷新申请列表。
5. GET `/pack-credits/access`：刷新积分余额/权限显示。
6. 仅本地模式（未配置Supabase登录）GET `/backups`；线上模式跳过备份请求。

本次没有拆出单独列表请求，也没有自动重复检查。POST成功后的后台刷新同样复用此函数。
