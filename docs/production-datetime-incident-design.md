## 2. 后端改动边界

### 2.1 写入统一为 UTC-aware，复用现有工厂

- 对此前清单中 **19 处 DateTime 列赋值**使用现有 `models.utc_now()`，语义为 `datetime.now(timezone.utc)`。来源获取模块按需导入同一工厂，不新造时钟类、全局 monkeypatch 或一套兼容框架。
- 主要为 main.py 的 `:476,1199,1280,1646,1839,1841,1865,1866,1899,1900,1919,1920,1991,2012,2031,2050,2759,3569` 与 source_acquisition.py`:136`。实施时按函数/字段重新定位，不依赖行号机械替换。
- `submitted_at` 有客户端值时走输入校验/UTC 规范化；没有时才用 utc_now，不用 `payload.submitted_at or utcnow()` 绕过边界。
- 现有模型的 created_at/updated_at 等默认工厂已 UTC-aware，保留，不把这次错误归到默认值。
- 不将 JSON 字符串时间、date 型 deadline/effective_date 一并改成 DateTime 列，不改历史 trace/指纹，不转换已有生产数据，不生成 schema 迁移。
- 现有 JSON 时间格式问题可另列后续事项；本次不为替换关键词而无差别修改非列写入。

### 2.2 B 路线的四个必须解决的风险

| 风险 | 设计决策 | 验收证据 |
|---|---|---|
| aware 与 naive 比较 | 不能混合排序/相减，也不能随意删 tzinfo。审计 outcome_learning.py`:99` 文档排序、main.py`:2082` 当前文档排序和积分过期/月界等；需要时只在明确读回/比较边界规范成 UTC | 旧记录与新记录混合排序、相等瞬间不同 offset、月界/过期时刻，不出现 TypeError 或八小时偏移 |
| 既有数据读回 | 仓库 PostgreSQL DDL 的关键日期列使用 timestamptz；旧 SQLModel/SQLite 或历史 schema 仍可能返回 naive。生产实际 schema 本次未查，不能假定全部一致。只对确认具有“服务端 UTC 时间”语义的 legacy 字段，在必要的读取/比较边界将 naive 解释为 UTC；未知来源的客户端本地时间不得猜测 | 隔离库建立旧记录/旧版本写入记录，重开 Session 后读取；验证绝对时刻、排序与后续保存，不只断言新建对象的 tzinfo |
| SQLite 与 PostgreSQL | SQLite 常不保留 timezone，旧 ORM 的读回行为也可能不同；PG timestamptz 与 timestamp without time zone 不能混为一谈。不得仅凭内存对象或 SQLite 通过宣布生产安全 | PG16 使用仓库 DDL建表；另测 legacy timestamp 布局，分别用 UTC 与 Australia/Perth 会话时区读写。若现有映射无法保持同一瞬间，阻断发布并单列兼容/迁移方案，不能暗中补迁移 |
| 客户端 naive submitted_at | 默认**拒绝 422**，不自动当本地或 UTC。有效 offset/Z 输入转为 UTC，None 由服务端生成；非法日期拒绝。验证发生在任何写入/积分动作之前 | Z、+08:00 同一瞬间等价；naive、非法字符串返回安全字段错误且不写数据；null/缺省行为明确 |

`datetime.replace(tzinfo=UTC)` 只适用于“已确认原值本来就是 UTC，只是缺标记”的 legacy 读回边界；正常 aware 输入使用 astimezone(UTC)。不全表扫改，不在 ORM 对象上无条件改写旧值，以免改变时间含义或引起意外 dirty update。

API 的时间戳输出也须在两组依赖下保留明确的 Z/offset，不能只在 Python 内部补比较而继续向浏览器输出没有时区的时间字符串。验收应直接检查响应和浏览器显示的同一瞬间；必要的响应规范化只作用于已确认 UTC 语义的字段，不改旧 trace/指纹字符串，不将 date 型字段改为 datetime。

现有普通前端未显式提交 submitted_at，因此拒绝 naive 主要影响 API/旧客户端；这仍是需要验收的输入契约变化。日期型 `effective_date`/deadline 继续按日历日期处理，不能附加午夜 UTC 造成日期变化。

积分 `now` 的显式测试/内部参数也应检查 aware，避免 `_month_start(now).astimezone()` 将 naive 当系统本地时间。现有 reserve/complete/release 已使用 aware；不因日期修复改变积分成本、幂等键、过期规则或全局限额。

## 5. 前端保存错误设计

### 5.1 已定位的缺口

`page.tsx:344–346` 和 `:370–372` 先 response.json() 再检查 response.ok，且没有覆盖 fetch/JSON 异常的 catch；非 JSON 500、空体或网络错误可在显示 notice 前抛出。`saveDetectedContact()` 的非 2xx 仅返回 false；全局 notice 在 `:1531`，不保证位于当前表单视野中。这解释了可能的静默路径，但未抓取生产那次 HTTP body，不能断言那次一定是非 JSON。

### 5.2 必须有的产品行为

- 资料主表单、申请内资料编辑、简历识别联系信息保存均覆盖；同时让用户验收的新建职位/编辑职位入口使用相同的小型安全响应处理，不重写所有 fetch 或引入新的请求框架。
- 每个保存入口有 idle/saving/saved/error 状态：开始时清旧错误并显示 Saving，禁重复点；try/catch/finally 保证网络/解析/服务器错误都退出 saving。
- 只有 HTTP 成功、响应可解析且具备必要字段才更新已保存状态；错误不得先清表单、清资料、显示成功或重置职位草稿。
- 表单保存按钮旁显示持续的 `role=alert` 错误，成功用 status；当前可见且可键盘/屏幕阅读器感知。失败保留当前输入，提供重试。401/403 明确提示登录/无权访问，遵守现有鉴权清理，不把个人草稿存入 localStorage。
- 500/502、HTML/纯文本/空体、畸形 JSON、200 无有效资料、网络拒绝/超时均有安全兜底。可显示已验证格式的 request id，**绝不原样展示服务端堆栈、SQL/参数、token 或连接串**。
- 422 显示安全的字段级校验说明；detail 是数组/对象时不能直接作为 React 文本渲染。
- 推荐普通保存失败文案：`We couldn't confirm your details were saved. Your input is still here. Please retry or reload to check.`；JSON 解析或网络超时不能武断宣称后端完全没写入。
- 识别联系信息失败但 CV 已上传时，分别提示“简历已上传，联系资料尚未确认保存”，不把已完成的上传误报为失败，也不暗示资料已经保存。

现有 save_profile 有多次 commit；UTC 修复不会自动将其变成单事务。此次不顺带重构事务边界；这也是失败文案必须区分“未确认”与“必定未保存”的原因。如要保证原子保存，需另列设计/批准。

### 5.3 前端测试

沿用现有 Node 测试验证响应处理；用已具备的 Playwright 依赖对本地页面/API stub 做实际表单验收，不连生产。覆盖：JSON 500、纯文本/HTML 500、空体、网络拒绝/超时、422 数组/对象、401、200 坏 JSON/缺字段，以及成功路径。断言错误确实可见、输入未被普通错误清空、按钮恢复、无假成功、无 raw SQL 字样/敏感字段；重复点击只有一个 in-flight 请求。覆盖主要资料表单、申请内编辑、识别保存和新建/编辑职位，不只测试一个未接入 UI 的 helper。
