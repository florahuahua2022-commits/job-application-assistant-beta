## 1. 推荐候选组

建议将已有 `backend/requirements.txt` 作为 CI 与生产共同的唯一三包约束来源，直接写 exact pins，避免再引入一份并行约束文件：

```text
sqlmodel==0.0.39
SQLAlchemy==2.0.52
pydantic==2.13.4
```

它替换当前 sqlmodel 范围，并显式加入另外两包；其他依赖本次保持原状。该段只是设计示意，没有写入真实 requirements。

依据：本地完整离线回归 633 项及 198 子测试通过、GitHub Actions 修正后的完整回归通过，真实 PostgreSQL 16 的窗口测试也通过；这是已经验证过的一组，不是随意取最新三个版本。证据来自之前执行记录，本次没有重跑。它尚不是完整生产 PostgreSQL/积分生命周期兼容证明。

## 2. 独立提交的文件边界

**真正从 main 独立落地时，最小业务提交只改 `backend/requirements.txt` 一个文件。** main 当前 CI 本来就读取这个文件；生产预期也读取同一文件。实施验收需确认实际安装入口是该文件，而不是另一个导出或忽略该文件的构建命令；不通过生产环境变量另加第二份约束。

这里有分支差异必须明确：`backend/tests/ci-constraints.txt` 以及 CI 的 `-c` 引用只存在于尚未合并的流量优化分支，main 上没有该文件。因此不能在 main 的独立小提交中“删除一个不存在的文件”，也不能为删它而顺带引入整套优化实现。

建议交付顺序（均等待实施批准）：

1. 从 main 独立提交三包 exact pins，运行隔离验收；获准后才考虑合并/部署该依赖提交。
2. 流量优化 PR 继续暂停。在恢复它之前，**追加新提交**，删除该分支的 `backend/tests/ci-constraints.txt`，从两个 CI 安装步骤删除 `-c backend/tests/ci-constraints.txt`，只保留 `-r backend/requirements.txt`；同步已批准的 main 依赖文件并重新验收。不 amend、不强推。
3. 最终进入 main 的 CI 和生产均只以 requirements 中这三个 exact pins 为准，不再维护 CI 专用的第二套版本。上述流量分支清理属于它恢复前的配套提交，不与独立 main 依赖提交混成一笔。

若用户希望文件结构上另设 `backend/constraints.txt`，也可以让 requirements 引用它并让所有入口使用同一路径，但会多一个文件和相对路径约定。本稿推荐已有 requirements 直接锁三包，改动最少。

## 3. 批准实施后必须做的隔离验收

- 在干净环境从同一 requirements 安装，验证实际解析出的三包版本完全一致，执行依赖一致性检查；不从当前虚拟环境的已安装包推断干净安装结果。
- 重跑 main 的完整离线回归。流量优化分支此前新增三项夹具含 naive 日期，这里如使用旧兼容组应按现有语义验收；未来修复新版兼容时再单独改夹具，不能先修夹具遮住业务写入失败。
- 用全新临时 PostgreSQL 16 和仓库 DDL/合成数据验证：已有资料更新、首次及替换简历、新建/编辑申请、source-aware 重建、上传来源、生成/编辑/SC 确认、投递/状态/归档/恢复。
- 同一隔离 PG16 验证积分预留、成功完结、生成失败释放、重试幂等、最后一个积分/全局额度并发；不能把原有两项 skip 当作已验证，也不使用生产数据。
- 重点核对时区存取及既有 timestamp 列的读写、旧生成 trace/输入指纹仍可读、启动 create_all 行为；不随依赖提交生成迁移、改数据库类型或补写历史时间。
- 依赖提交不连接生产。生产部署需要另外明确授权和事前访问/变更记录；部署日志只能证明安装/启动，不能替代上述业务验收。
